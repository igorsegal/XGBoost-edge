Population-Based Optimization Algorithms: Building a Defense Against Cheaters

MetaTrader 5 — Trading | 21 October 2026 at 07:13
578 0
Andrey Dik

Table of Contents

  1. Introduction
  2. Test Results
  3. Composite Test
  4. Conclusions


Introduction

In the previous article, we found that certain algorithms can receive inflated scores not because of the quality of their search, but because of a chance match between their internal mechanics and the geometry of the test functions. We identified the nature of the phenomenon, formulated diagnostic criteria, and adjusted the Forest and Megacity test functions. This eliminated the possibility of gaining an advantage due to search agents moving "diagonally" in a two-dimensional plane. The article concluded with a plan: to run all the algorithms on the updated test bench and recalculate the rankings.

This article carries out that plan. All 45 algorithms from the ranking table were retested using the adjusted test functions. In addition to the recalculation, a composite test for detecting “cheating” was developed. Instead of optimizing a single function with repeating coordinates, the agent simultaneously optimizes five different functions with different landscapes. An algorithm with an artificial directional bias cannot simultaneously “guess” the optimum on five different surfaces, whereas an honest search mechanism will show very similar results on both the updated test functions and the new multi-function test. Its purpose is to quickly and definitively determine whether an algorithm has actual search capability before running the full test bench. This is a kind of entry filter that weeds out dummy algorithms at an early stage. This is not about revising the methodology, but about eliminating a few exceptions that exploited the specific location of the extrema.

After reading this, the trader will receive an updated ranking table — free of algorithms with artificially inflated results — and a ready-to-use script for independently testing any new algorithm before entrusting it with the optimization of their strategy.

The results of running the algorithms on the updated test bench have been obtained and are ready to be entered into the ranking table. However, before doing that, it makes sense to take one more step, which will be discussed below.

Our research has shown that some optimization algorithms may produce inflated results on certain test functions — not because of the quality of the search, but due to a random coincidence between the algorithm’s internal mechanics and the geometry of the function’s landscape. For example, if the algorithm generates trajectories primarily along the diagonal of the search space, and the global maximum lies on that diagonal, then the optimal solution will be easier to find. This does not reflect the algorithm's actual search capability.

HHO demonstrated a suspiciously high result on the Forest function — over 93% — even though on Hilly of the same dimensionality it showed only about 58%. This discrepancy went beyond the usual range of variation and required a detailed investigation. An analysis of the algorithm’s internal mechanics revealed that the scalar multipliers in the HHO formulas generate predominantly diagonal search trajectories, and that the global maximum of Forest was located right near the diagonal of the space. The algorithm was not so much searching for the optimum as systematically running into it because its direction of movement coincided with the geometry of the landscape. We called this phenomenon “cheating.”

The standard test bench runs each of the three test functions (Hilly, Forest, Megacity) independently, at three dimensionality levels: 10, 50, and 1,000 coordinates of the same function. In this case, all of the agent's coordinate pairs optimize the same surface. An algorithm with a systematic bias in a certain direction can exploit this uniformity.

A composite test was developed to identify such behavior at an early stage. The principle is simple: instead of 10 coordinates from a single function (5 pairs), we use 5 different functions — Hilly, Forest, Megacity, Peaks, and Skin. Each function is assigned a single pair of coordinates. Each pair lives in its own landscape and has its own permissible range: Hilly is optimized in [-3, 3], Forest in [-42.5, -37] × [-45, -39.8], Megacity in [-10, -2] × [-10.5, 10], and so on. An agent's final fitness is calculated as the average of the Core() values across all five functions.

A key property of the test is that the algorithm cannot “cheat” on it in the same way it can cheat on a single function. Any cheating technique — for example, one that works for Forest — is useless for Hilly or Megacity, with their completely different geometries and different coordinate ranges. To achieve a high score on the composite test, the algorithm must genuinely be able to find the optimum independently in each of the five different landscapes.

Interpreting the results is simple. If the algorithm is “honest,” its result on the composite test will roughly correspond, with only a small deviation, to the average result of the standard test bench's first test (with 5 functions) on the same functions. However, if the algorithm inflates its result on any single function due to a geometric match, this advantage will disappear on the composite test, and the difference between the standard and composite tests will be significant. The greater this discrepancy, the more the algorithm exploits the characteristics of a specific function instead of performing a real search.


Composite Test

The Test_AO_AntiCheat script is designed to be as simple as possible and does not require visualization — only outputting the results to the log.

At startup, the optimization algorithm is selected from a drop-down list via the AOexactly_P parameter, allowing you to quickly switch between any algorithms without recompiling. The two remaining parameters specify the number of function evaluations (NumbTestFuncRuns_P) and the number of repeated runs (NumberRepetTest_P).

At the start, the script creates five test function objects: Hilly, Forest, Megacity, Peaks, and Skin. Next, the rangeMin and rangeMax arrays are created, each 10 elements long (5 coordinate pairs). Each pair receives its search bounds from its function: elements 0–1 are filled with the Hilly domain, elements 2–3 with the Forest domain, and so on. The rangeStep array is filled with zeros because argument discretization is not used.

The number of epochs is calculated in the standard way: the total number of function evaluations is divided by the population size. Next, the main loop of repeated runs begins. In each run, the algorithm is reinitialized, and the inner loop over epochs executes the standard sequence: calling Moving(), calculating fitness, and calling Revision().

The fitness calculation is the only difference from the standard script. Instead of calling f.CalcFunc(ao.a[set].c), which passes all coordinates to a single function, a loop over the five functions is executed for each agent. Each function receives its own coordinate pair via a direct call to Core(x, y); the results are summed and divided by five. Since all functions return normalized values in the range [0, 1], the final fitness also lies in [0, 1].

After each run, the achieved result ao.fB is logged. Once all runs are complete, the average value and its percentage representation are displayed. This percentage is an indicator. It is enough to compare it with the average value of the first test on the standard test bench to assess the algorithm's "honesty."

//+------------------------------------------------------------------+
void OnStart()
 {
  C_AO *AO = SelectAO(AOexactly_P);

  if(AO == NULL)
   {
    Print("AO is not selected...");
    return;
   }

  Print(AO.GetName(), "|", AO.GetDesc(), "|", AO.GetParams());

//--- create 5 functions
#define NFUNCS 5
  C_Function *funcs [NFUNCS];
  funcs [0] = new C_Hilly();
  funcs [1] = new C_Forest();
  funcs [2] = new C_Megacity();
  funcs [3] = new C_Peaks();
  funcs [4] = new C_Skin();

//--- 10 coordinates: pair 0-1 = Hilly, 2-3 = Forest, 4-5 = Megacity,
//                   6-7 = Peaks, 8-9 = Skin
  int params = NFUNCS * 2;

  double rangeMin  [];
  double rangeMax  [];
  double rangeStep [];
  ArrayResize(rangeMin,  params);
  ArrayResize(rangeMax,  params);
  ArrayResize(rangeStep, params);

  for(int i = 0; i < NFUNCS; i++)
   {
    rangeMin  [i * 2]     = funcs [i].GetMinRangeX();
    rangeMax  [i * 2]     = funcs [i].GetMaxRangeX();
    rangeStep [i * 2]     = 0.0;

    rangeMin  [i * 2 + 1] = funcs [i].GetMinRangeY();
    rangeMax  [i * 2 + 1] = funcs [i].GetMaxRangeY();
    rangeStep [i * 2 + 1] = 0.0;
   }

//--- run tests
  int    epochCount = NumbTestFuncRuns_P / (int)AO.params [0].val;
  double aveResult  = 0.0;

  Print("=============================");
  Print("Composite test: Hilly + Forest + Megacity + Peaks + Skin");
  Print("Coordinates: ", params, "; Epochs: ", epochCount,
        "; Repeats: ", NumberRepetTest_P);
  Print("=============================");

  for(int test = 0; test < NumberRepetTest_P; test++)
   {
    if(!AO.Init(rangeMin, rangeMax, rangeStep, epochCount))
      break;

    for(int epochCNT = 1; epochCNT <= epochCount && !IsStopped(); epochCNT++)
     {
      AO.Moving();

      //--- calculate fitness for each agent
      for(int set = 0; set < ArraySize(AO.a); set++)
       {
        double sum = 0.0;
        for(int i = 0; i < NFUNCS; i++)
         {
          sum += funcs [i].Core(AO.a [set].c [i * 2],
                                AO.a [set].c [i * 2 + 1]);
         }
        AO.a [set].f = sum / NFUNCS;
       }

      AO.Revision();
     }

    Print("Run ", test + 1, "/", NumberRepetTest_P, ": ", AO.fB);
    aveResult += AO.fB;
   }

  aveResult /= (double)NumberRepetTest_P;

  Print("=============================");
  Print("Average result: ", DoubleToString(aveResult, 10),
        " (", DoubleToString(aveResult * 100.0, 2), "%)");
  Print("=============================");

//--- release
  for(int i = 0; i < NFUNCS; i++)
    delete funcs [i];
  delete AO;
 }
//+------------------------------------------------------------------+

Conclusion: the test clearly divided the algorithms into two groups. ANS and CLA demonstrated that their search mechanism works universally. DOAm and HHO lost about 20 percentage points — this is the portion of their standard score that was attributable to “luck” with the geometry of individual functions, rather than to actual search ability.

Therefore, DOAm and HHO will not be included in our ranking table, as including such algorithms in the ranking would distort the overall picture and mislead readers regarding their actual effectiveness.

After the test functions were updated (the Megacity maximum and the Forest adjustment), the ranking table was completely recalculated. A comparison of the old and new results showed that most algorithms maintained their positions, with only minor deviations. Several algorithms improved their scores by 4–6 points: SSG (+5.8), AMOm (+5.4), SDSm (+5.2), (PO)ES (+5.0), and SIA (+4.7). Some showed a slight decrease: BOAm (−1.8), BSA backtracking (−1.9), CSO (−1.6). A number of algorithms — CTA, ECBO, DOA, and FBA — changed by less than 1 percentage point. Overall, the discrepancies were within expectations: changes in the geometry of the test functions naturally redistribute the results; the new landscape suits some algorithms slightly better, while others perform slightly worse.

However, one algorithm raised questions: HS (Harmony Search). Its overall score rose from 52.79% to 60.60%, an increase of 7.8 percentage points — significantly more than the others. Moreover, all of the improvement came from a single function: the score on the first Megacity test rose from 0.620 to 0.917, and the total Megacity score rose from 1.097 to 1.698. On the Hilly and Forest functions, the HS results remained virtually unchanged. Such a sharp jump on one specific function required verification: did HS truly become better at searching, or did its mechanics just happen to align with the new Megacity geometry?

To answer this question, we ran HS through a composite test. HS is clean. 92.45% is roughly at the level of ANS (98.38%) and CLA (96.70%) on the same composite test.

Conclusions

In this article, we have completed the work we began in the previous article: we moved from diagnosing the problem to fully resolving it. Key findings:

  • All 45 algorithms were tested on the updated test functions, with the ranking table recalculated. The vast majority of algorithms produced results close to their previous ones: deviations ranged from fractions of a percent to 5–6 percentage points, which falls within the natural scatter caused by changes in the landscape. This confirmed the reliability of the test bench as a tool: its methodology works correctly, and the identified problem concerned only a few outlier algorithms.
  • The HHO and DOAm algorithms were identified as “cheaters” and removed from the ranking table. The composite test showed a score of about 53% for them — a level not comparable to their previous scores on the standard test bench (68% and 73%). By comparison, the algorithms at the top of the table — ANS, CLA, and HS — achieved scores of 96–99% on the same composite test, confirming the universality of their search mechanism.
  • A script for a composite test of resistance to geometric bias has been developed. Five different functions (Hilly, Forest, Megacity, Peaks, Skin), each with different domains and landscapes, are combined into a single problem with 10 coordinates. A single run of this script takes a few seconds and provides a definitive answer: if the result is significantly lower than the average for the first test on the standard test bench, the algorithm is exploiting the geometry rather than searching. It is recommended to use this script as an initial filter before a full run on the test bench.

For a practicing trader, all of this is of direct importance. Optimization algorithms are widely used in trading — to tune the parameters of trading strategies, configure indicators, and optimize portfolios. If an algorithm overstates its results on test problems due to an accidental match with their geometry, then on real-world problems it will produce parameters that are far from optimal and create a false impression of optimization quality. Our toolkit for detecting "cheating" helps weed out such algorithms as early as the selection stage and use only those that truly have a high-quality search mechanism.

Practical advice for traders: before using a new optimization algorithm to select parameters for a trading strategy, run it through a composite test. If the result of the composite test differs significantly from the results of the standard test bench, do not trust that algorithm: it will fail to handle a real-world task just as it fails the composite test. All the tools described — the composite test script, the updated test functions, and the 3D visualization panel — are included with the article and are ready to use.
